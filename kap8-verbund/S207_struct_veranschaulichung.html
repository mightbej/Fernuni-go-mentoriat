1. Motivation: Warum Verbunde?

Der Studienbrief fuehrt Verbunde nicht als bloe neue Schreibweise ein, sondern als Antwort auf ein konkretes Modellierungsproblem: Daten einer Person gehoeren zusammen, sind aber nicht alle vom selben Typ. Arrays koennen viele Werte speichern, aber nur desselben Typs. Ein struct fasst dagegen heterogene Daten unter einem gemeinsamen Typ zusammen.

2. Einen struct-Typ lesen

In Go wird ein Verbund mit dem Schluesselwort struct beschrieben. Die uebliche Schreibweise ist zeilenweise. Gerade bei mehreren Feldern ist das die lesbarste Form.

struct { vorname string nachname string gebJahr int ort string verheiratet bool }
Wichtig: Hinter die Typangabe eines Felds kommt kein Komma. Jedes Feld steht ueblicherweise in einer eigenen Zeile.
Lesetraining: Lies einen struct immer als Liste von Feldern: Wie heisst die Komponente und welchen Typ hat sie?

3. Felder deklarieren

Jedes Feld braucht einen eindeutigen Namen und einen Typ. Aufeinanderfolgende Felder desselben Typs duerfen auch kompakt zusammen notiert werden. Beides beschreibt denselben Datenaufbau.

// ausfuehrlich struct { vorname string nachname string gebJahr int ort string verheiratet bool } // kompakter fuer gleiche Typen struct { vorname, nachname string gebJahr int ort string verheiratet bool }
RegelBedeutung
Eindeutiger Feldnamesonst ist ein Zugriff nicht eindeutig
Typ pro Feldjedes Feld gehoert fest zu einem Datentyp
Gruppierung gleicher Typennur Schreibkuerzung, kein anderer Semantikwechsel

4. Die Reihenfolge der Felder gehoert zum Typ

Ein typischer Denkfehler ist: gleiche Feldnamen und gleiche Feldtypen reichen aus. Laut Studienbrief ist das nicht genug. Auch die Reihenfolge der Felder bestimmt die Typidentitaet.

struct { vorname, nachname, ort string gebJahr int verheiratet bool } struct { nachname, vorname, ort string verheiratet bool gebJahr int }
Achtung: Andere Feldreihenfolge bedeutet anderer Datentyp. Zwei struct-Typen koennen also trotz aehnlicher Felder unvertraeglich sein.
Kurztest: Welche Literal-Schreibweise bleibt robuster, wenn sich die Feldreihenfolge spaeter aendert?

6. Exportierte und nicht exportierte Namen

Der Studienbrief erinnert daran, dass fuer struct-Typen dieselben Exportregeln gelten wie fuer andere Bezeichner in Go. Grossbuchstaben am Anfang exportieren, Kleinbuchstaben bleiben paketintern.

type Person struct { Vorname string Nachname string } type person struct { vorname string nachname string }

Studienbrief-Konvention: Die Beispiele bleiben klein geschrieben, weil sie bewusst nicht exportiert werden sollen.

7. Nullwert eines Verbund-Typs

Wird bei einer struct-Variable kein Initialwert angegeben, dann erhaelt sie den Nullwert ihres Typs. Dieser setzt sich Feld fuer Feld aus den jeweiligen Nullwerten zusammen.

var anna, karl person fmt.Println(anna, karl) // { 0 false} { 0 false}
string

Nullwert ist leere Zeichenkette "".

int

Nullwert ist 0.

bool

Nullwert ist false.

Merksatz: Der Nullwert eines struct ist kein eigener Sonderwert, sondern die Zusammensetzung der Nullwerte aller Felder.

8. Verbund-Literale: erste Syntax-Variante

Die erste Schreibweise funktioniert rein positionsbasiert. Alle Feldwerte muessen angegeben werden, und zwar genau in der Reihenfolge der struct-Definition.

anna = person{"Anna", "Schmidt", 1966, "Hamburg", false} // unzulaessig, weil unvollstaendig // anna = person{"Anna", "Schmidt", 1966, "Hamburg"}
Risiko: Wenn spaeter die Feldreihenfolge geaendert wird, muessen alle positionsbasierten Literale mit angepasst werden. Besonders heikel wird das, wenn zwei Felder denselben Typ haben.

9. Verbund-Literale: zweite Syntax-Variante

Die zweite Schreibweise nennt jedes Feld explizit. Dadurch duerfen Feldname-Wert-Paare in beliebiger Reihenfolge stehen, und fehlende Felder erhalten automatisch ihren Nullwert.

karl = person{ nachname: "Mueller", vorname: "Karl", ort: "Koeln", gebJahr: 1955, // verheiratet: false wird implizit ergaenzt }
Praxisvorteil: Diese Schreibweise ist unabhaengig von der Feldreihenfolge und im Studienbrief die empfohlene alltagstaugliche Variante.
Syntax-Detail: In der mehrzeiligen Form muss auch nach dem letzten explizit notierten Feld ein Komma stehen.

10. Ausgabe von struct-Werten

Fuer die Ausgabe reicht nicht nur irgendein Print. Der Studienbrief unterscheidet drei nuetzliche Blickwinkel: nur Werte, Feldnamen mit Werten und Ausgabe in Literal-Syntax.

fmt.Printf("%v\n", anna) fmt.Printf("%+v\n", anna) fmt.Printf("%#v\n", anna)
FormatWas wird sichtbar?Nutzen
%vnur Feldwerteschnelle Normalansicht
%+vFeldnamen und Wertegut zum Lernen und Debuggen
%#vGo-aehnliche Literal-Syntaxzeigt die Struktur besonders explizit

11. Feldvariablen und Punktnotation

Eine struct-Variable besteht aus Feldern, und jedes Feld ist selbst wieder eine Variable. Der Zugriff erfolgt mit Punktnotation. Genau hier wird sichtbar, dass ein Verbund nicht nur gesammelt speichert, sondern seine Teile gezielt ansprechbar haelt.

var anna = person{"Anna", "Schmidt", 1966, "Hamburg", false} anna.nachname += "-Schiller" anna.verheiratet = true fmt.Println(anna.nachname, anna.verheiratet)
Verbund-Variable
anna
Feld-Variablen
anna.nachname
anna.verheiratet
Punktnotation: Der Punkt verbindet die Verbund-Variable mit einem konkreten Feld. So wird aus dem grossen Gesamtwert ein gezielt bearbeitbares Teilstueck.

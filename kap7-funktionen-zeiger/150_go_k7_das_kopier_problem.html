Das Kernproblem: Zwei teure Kopieroperationen

Wenn wir ein Array an eine Funktion übergeben, geschehen zwei vollständige Kopieroperationen:

Kopiervorgang 1: main() → swap()
[42, 7, 19, 88, 3, 25, 71, 14, 60, 9]
↓ Komplette Kopie ↓
[42, 7, 19, 88, 3, 25, 71, 14, 60, 9] (in swap)

In der Funktion: Nur zwei Elemente ändern!

Kopiervorgang 2: swap() → main() (Rückgabe)
[7, 42, 19, 88, 3, 25, 71, 14, 60, 9] (verändert)
↓ Komplette Kopie zurück ↓
[7, 42, 19, 88, 3, 25, 71, 14, 60, 9] (in main)
Das Unbehagen: Wir kopieren das gesamte Array zweimal – aber verändern nur 2 Positionen. Das ist nicht nur verschwendet – das ist sehr teuer!
Warum ist Kopieren überhaupt teuer? Das ist die wichtigere Frage. Wir werden gleich sehen.

Warum ist Kopieren so teuer?

Es geht nicht nur um "Bytes zählen". Kopieren ist fundamental teuer wegen mehrerer Gründe:

1. Der Prozessor ist viel schneller als der Speicher

Asymmetrie:
  • Prozessor-Geschwindigkeit: ~3-4 GHz (3-4 Milliarden Operationen/Sekunde)
  • RAM-Zugriffszeit: ~100-200 Nanosekunden
  • Faktor: Der Prozessor ist ca. 100-1000x schneller als RAM!

Das bedeutet: Jedes Mal, wenn der Prozessor Daten aus dem RAM kopieren muss, wartet er. Der schnelle Chip sitzt "untätig" und wartet auf den langsamen Speicher.

2. Das Betriebssystem muss Speicher verwalten

Speicher-Allokation:
  • Das OS muss freien Speicher suchen für die neue Kopie
  • Das OS muss diesen Speicher reservieren und markieren
  • Viele Speicher-Management-Operationen sind nötig (Fragmentierung, Bookkeeping)
  • Diese Operationen sind teuer und verursachen viele RAM-Zugriffe

3. Kontext-Wechsel und Betriebssystem-Overhead

Was während einer Kopieroperation passiert:
  • Der Prozessor arbeitet mit Speicher-Lese- und Schreib-Operationen
  • Das OS kann einen Kontext-Switch auslösen (Prozess-Wechsel)
  • Der Prozessor muss seinen aktuellen Zustand speichern und einen anderen Prozess laden
  • Das ist extrem teuer: CPU-Caches werden geleert, Speicher-Zuordnungen ändern sich

4. Cache-Misses und Memory Stalls

CPU-Caches:
  • Der Prozessor hat kleine, schnelle Caches (L1, L2, L3) für häufig verwendete Daten
  • Wenn Daten nicht im Cache sind → Cache-Miss
  • Der Prozessor muss auf den RAM warten → Memory Stall
  • Während dieser Zeit macht der Prozessor nichts (CPU-Wartezyklen)
Zusammenfassung: Warum Kopieren so teuer ist
  • Viele RAM-Zugriffe (teuer wegen Speicher-Latenz)
  • Speicher-Management durch das OS (teuer)
  • Mögliche Kontext-Switches (sehr teuer)
  • Cache-Misses und CPU-Stalls (teuer)

Das alles addiert sich: Der Prozessor sitzt wartend herum!

Praktische Konsequenz: Ein schlecht programmierter Sortieralgorithmus kann durch unnötige Kopieren um den Faktor 100-1000x langsamer sein. Ein Problem, das bei effizienter Programmierung 4 Sekunden dauert, braucht dann etwa 1 Stunde!

Einfaches Beispiel: swap() aufgerufen

Hier ist die ganze Aktion Schritt für Schritt:

func swap(a [10]int, i int, j int) [10]int { a[i], a[j] = a[j], a[i] // Nur 2 Elemente ändern return a } func main() { a := [10]int{42, 7, 19, 88, 3, 25, 71, 14, 60, 9} a = swap(a, 0, 1) // Tausche Positionen 0 und 1 }
Schritt 1: Aufruf

swap(a, 0, 1)

→ Das ganze Array wird zur Funktion kopiert


Schritt 2: Änderung in der Funktion

Nur a[0] und a[1] werden getauscht


Schritt 3: Rückgabe

Das ganze Array wird zurück kopiert


Schritt 4: Zuweisung in main()

a = ... speichert die Kopie

Bilanz: Für einen Tausch von 2 Elementen haben wir das Array zweimal vollständig kopiert!

Speicher-Diagramm: Was passiert im RAM

So sieht es aus, wenn wir swap() aufrufen:

MAIN():
a = [42, 7, 19, 88, 3, 25, 71, 14, 60, 9]

↓ Aufruf: swap(a, 0, 1)

SWAP() - PARAMETER

(10 Bytes kopieren)

a (Kopie) = [42, 7, 19, 88, 3, 25, 71, 14, 60, 9]

Ändere a[0] und a[1]:

a = [7, 42, 19, 88, 3, 25, 71, 14, 60, 9]

↓ return (10 Bytes kopieren)

MAIN() - NACH RÜCKGABE:
a = [7, 42, 19, 88, 3, 25, 71, 14, 60, 9]
Beobachtung: Die Kopie in swap() existiert nur für einen Moment. Danach wird sie gelöscht. Reine Verschwendung!

Wie schlecht ist es? Größe des Arrays

Der Kopier-Aufwand ist proportional zur Array-Größe.

Array-Größe Speicher pro Element Beim Aufruf kopiert Bei Rückgabe kopiert Gesamt für einen Tausch
[10]int 8 Byte 80 Byte 80 Byte 160 Byte
[100]int 8 Byte 800 Byte 800 Byte 1.600 Byte
[1000]int 8 Byte 8 KB 8 KB 16 KB
[1.000.000]int 8 Byte 8 MB 8 MB 16 MB
Realisierung: Bei einem Array mit einer Million Elementen kopieren wir 16 MB Speicher – nur um zwei Elemente zu tauschen!

Praxisbeispiel: Selection Sort mit 100 Elementen

Selection Sort macht etwa 99 Tausche (einen pro Runde). Jeder Tausch kopiert das komplette Array:

Szenario: Array mit 100 Elementen
  • Größe eines Elements: 8 Byte (int64)
  • Größe des Arrays: 100 × 8 = 800 Byte
  • Tausche beim Sortieren: ≈ 99
  • Pro Tausch: 800 Byte hin + 800 Byte zurück = 1.600 Byte
  • Gesamt für Sortieren: 99 × 1.600 = 158.400 Byte = 155 KB
Frage: Aber was ändert sich wirklich?
  • Pro Tausch: 2 Elemente (16 Byte) werden getauscht
  • Kopier-Overhead: 1.600 Byte
  • Verbreiteter Faktor: 100:1

Die Bilanz: Der Overhead wächst mit O(n²)

Das Problem wird noch schlimmer: Der Kopier-Overhead ist nicht konstant – er wächst quadratisch mit der Array-Größe!

Analyse für Selection Sort

Die mathematische Realität:
  • Algorithmus selbst: O(n²) – das ist unvermeidbar
  • Pro Tausch: Array wird 2× kopiert = 2×O(n)
  • Anzahl der Tausche: ~n Tausche
  • Gesamt-Kopier-Overhead: n × 2×O(n) = O(n²)

Erkenntnis: Der Kopier-Overhead ist genauso teuer wie der Algorithmus selbst!

Konkrete Zahlen für Selection Sort

Array-Größe (n) Algorithmus-Operationen Kopier-Overhead Verhältnis
100 Elemente ~10.000 Vergleiche ~200 Array-Kopien (je 800 Byte) 1:1 – Kopieren ist genauso teuer!
1.000 Elemente ~1.000.000 Vergleiche ~2.000 Array-Kopien (je 8 KB) 1:1 – Immer noch genauso teuer!
10.000 Elemente ~100.000.000 Vergleiche ~20.000 Array-Kopien (je 80 KB) 1:1 – Das Kopieren dominiert!
Wichtigste Erkenntnis:

Der Kopier-Overhead ist nicht einfach ein konstanter Faktor – er wächst O(n²) zusammen mit dem Algorithmus!

Das bedeutet: Bei großen Arrays wird die Hälfte (oder mehr!) der Rechenzeit für unnötige Kopieroperationen verschwendet.

Praktisch: Ein Problem, das 1 Stunde dauert, könnte in wenigen Minuten gelöst sein – nur durch effiziente Programmierung ohne extra Kopien!

Die Lösung: Zeiger statt call-by-value

Mit Zeiger-Parametern übergeben wir nicht das Array, sondern nur die Speicher-Adresse. Das ist fundamental effizienter!

Vergleich: call-by-value vs. call-by-reference

Call-by-value (ALT):
Ganzes Array kopiert (z.B. 100 Elemente = 800 Byte)

× 2 (hin und zurück)

= 1.600 Byte pro Tausch!


Call-by-reference mit Zeiger (NEU):
Nur Adresse übergeben (8 Byte)

× 2 (hin und zurück)

= 16 Byte pro Tausch!

Die Einsparung für ein Array mit 100 Elementen:
  • call-by-value: 1.600 Byte pro Tausch
  • call-by-reference: 16 Byte pro Tausch
  • Faktor: 100× weniger Speicher-Traffic!

Der Code-Unterschied

// ALT: call-by-value func swap(a [100]int, i int, j int) [100]int { a[i], a[j] = a[j], a[i] return a // Ganzes Array zurück! } // NEU: call-by-reference mit Zeiger func swap(a *[100]int, i int, j int) { a[i], a[j] = a[j], a[i] // Nichts zurück, Original wird direkt verändert }
Was ändert sich:
  • Parameter: *[100]int statt [100]int
  • Kein return mehr – die Funktion ändert das Original direkt
  • Aufruf: swap(&a, i, j) statt a = swap(a, i, j)

Asymptotischer Gewinn

Rechenzeit für Selection Sort mit Zeigern:
  • Ohne Zeiger (call-by-value): Algorithmus O(n²) + Kopier-Overhead O(n²) = zusammen O(n²) mit großem Faktor
  • Mit Zeiger (call-by-reference): Algorithmus O(n²) + Kopier-Overhead O(1) (nur Adressen!) = zusammen O(n²) mit kleinerem Faktor

Der O(n²) Faktor halbiert sich oder wird noch viel besser!

Die große Erkenntnis: Zeiger-Parameter sind nicht nur eine Optimierung – sie sind eine fundamentale Programmier-Technik. Sie trennen:
  • Logik (was der Algorithmus tut)
  • Speicher-Effizienz (wie der Code implementiert ist)
Mit dieser Trennung können Funktionen eleganter, klarer und 100-1000x schneller sein!
